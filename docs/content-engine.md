# 콘텐츠 엔진

검색으로 들어온 사람을 조회 도구(주소 → 건축물대장 → 허가일 기준 소방시설 기준)로 이끄는 정적 콘텐츠를 만드는 생성기다.
Cloudflare Pages 는 빌드 없이 `main` 을 그대로 배포하므로, **생성한 HTML 도 커밋한다.**

- 기준 페이지(용도별·시설별)는 `data/` 에서 **자동 생성**되고 항상 렌더링된다.
- 글(법령 개정 소식·실무 가이드·질문·사례)은 **Claude 가 초안 → 소유자가 검수 → 승인 → PR 병합**으로 게시된다.
  `status: approved` 인 글만 렌더링되므로 초안은 병합돼도 게시되지 않는다.

```bash
node scripts/content/build.mjs                  # 생성 (결과를 커밋한다)
node scripts/content/build.mjs --check          # 커밋된 결과가 최신인지 (CI, 다르면 exit 1)
node --test scripts/content/test/*.test.mjs     # 테스트 (Node 22 는 폴더 인자를 받지 않아 셸 글롭으로)
node scripts/content/build.mjs --drafts --out "$(node -e "console.log(require('os').tmpdir())")/sobangcheck-preview"
                                                # 초안까지 렌더링한 미리보기 (저장소 밖에만 쓴다)
```

의존성 없음(Node 22, `npm install` 하지 않는다). 시계를 쓰지 않아 같은 입력이면 항상 같은 출력이 나온다.
종료 코드: 0 성공, 1 결과가 오래됨(`--check`), 2 콘텐츠·데이터 오류(파일·줄 번호를 알려 준다).

## 구조

```
data/*.json ───────────────┐
content/config.json         │                         standards/index.html
content/static-pages.json   ├─ scripts/content/build.mjs ─▶ standards/use/*.html, standards/facility/*.html
content/{news,guide,qa}/*.md│   (lib/*.mjs)              news/*.html, news/index.html, news/feed.xml
js/components.js (푸터)      │                         qa/*.html, qa/index.html
index.html·pages/·guide/ ───┘                         guide/<생성 글>.html, guide/articles.html, sitemap.xml
```

| 파일 | 역할 |
|---|---|
| `scripts/content/build.mjs` | CLI. 메모리에서 전부 만든 뒤 쓰기(`writeOutputs`) 또는 비교(`checkOutputs`) |
| `lib/markdown.mjs` | Markdown 부분집합 렌더러 (아래 "본문 문법") |
| `lib/frontmatter.mjs` | 프론트매터 파서 (YAML 부분집합) |
| `lib/data.mjs` | `data/` 읽기·검사, 법령 연혁 도우미, 데이터 기준일 검사 |
| `lib/standards.mjs` | 기준 페이지 (허브·용도·시설) |
| `lib/posts.mjs` | 글 검사·렌더링, 유형별 색인 |
| `lib/feeds.mjs` | 손으로 쓴 페이지 찾기, `sitemap.xml`, RSS 2.0 |
| `lib/template.mjs` | 공통 틀: 메타·OG·트위터·JSON-LD, 헤더·푸터, 조회 안내·출처·관련 링크 |
| `lib/config.mjs` | 고정 설정: 얇은 페이지 문턱값, 가이드 연결, 직접 입력 용도 연결, 글 유형 |
| `css/content.css` | 생성 페이지 스타일 (`ce-` 접두사, style.css 변수로 다크 모드) |
| `content/config.json` | `dataVerified`(데이터 기준일), `standardsPublished`(기준 페이지 첫 게시일) |
| `content/static-pages.json` | 손으로 쓴 페이지의 사이트맵 순서·changefreq·priority·lastmod |
| `content/topics.json` | 검색 주제 백로그 |

생성 HTML 은 둘째 줄에 `<!-- generated by scripts/content/build.mjs … -->` 표시가 있다. 빌드는 **이 표시가 있는 파일만**
덮어쓰거나 지운다. 글 슬러그가 손으로 쓴 파일(예: `guide/sprinkler.html`)과 겹치면 빌드가 멈춘다.
`sitemap.xml`·`news/feed.xml` 은 생성기 소유다 — 직접 고치지 말고 설정을 고친 뒤 다시 생성한다.

## 콘텐츠 유형과 URL

주소는 확장자 없이 쓴다(Cloudflare Pages 가 `/x` 에 `x.html` 을 준다). canonical·사이트맵·내부 링크 모두 같은 규칙.

| 유형 | 원본 | URL | 목록 | JSON-LD |
|---|---|---|---|---|
| 기준 허브 | `data/` | `/standards/` | — | CollectionPage |
| 용도별 기준 | `data/NN_<이름>.json` | `/standards/use/<이름, _→->` (예: `02_neighborhood_facilities` → `neighborhood-facilities`) | 허브 | Article |
| 시설별 기준 | `data/facilities.json` + 용도 파일 | `/standards/facility/<id, _→->` (예: `auto_fire_detection` → `auto-fire-detection`) | 허브 | Article |
| 법령 개정 소식 | `content/news/<slug>.md` | `/news/<slug>` | `/news/` + RSS `/news/feed.xml` | NewsArticle |
| 실무 가이드 | `content/guide/<slug>.md` | `/guide/<slug>` | `/guide/articles` | Article |
| 질문·사례 | `content/qa/<slug>.md` | `/qa/<slug>` | `/qa/` | Article (+ 화면에 FAQ 가 있으면 FAQPage) |

모든 페이지에 BreadcrumbList 가 붙는다. 손으로 쓴 `guide/index.html` 은 이 PR 에서 건드리지 않는다 — 생성 가이드 목록
`/guide/articles` 를 나중에 거기서 링크하면 된다. `data/00_house.json`(다른 PR)이 들어오면 `/standards/use/house` 가 저절로 생긴다.

### 기준 페이지가 보여 주는 것 (데이터에 있는 것만)

- **용도 페이지**: 용도 정의(원문 요약)·하위 구분, "허가일에 따라 기준이 다릅니다" 설명(그 용도의 실제 개정 쌍을 예로),
  시설별 기간표(적용 기간 | 기준(원문 요약) | 대상 | 비고·근거) — 행마다 현행·종료·시행 예정 표시, 최근 개정·변경
  (시작일·종료일에서 계산, 같은 날 시행된 법령·고시 링크), 관련 화재안전기준(NFPC·NFSC 현행판), 조회 안내(직접 입력 용도 안내 포함),
  출처(현행 시행령·법, 비고에 인용된 개정 법령, 화재안전기준 — 모두 law.go.kr).
- **시설 페이지**: 용도별 현행 기준(데이터 기준일 현재), 시행 예정 기준, 변경 이력, 화재안전기준 현행판과 최근 개정 5건,
  손으로 쓴 가이드 연결(`GUIDE_BY_FACILITY`), 조회 안내, 출처. 표 안에서 되풀이되는 비고는 표 아래 주석으로 한 번만 싣는다.
- **허브**: 용도 목록(시설 수·기준 수), 시설 목록(분류별), 최근 법령·화재안전기준 개정 10건, 새 글.

"같은 날 시행된 개정"은 시행일이 같다는 사실만 보여 주며 근거라고 주장하지 않는다(페이지에 그렇게 적는다). 근거는 비고(`note`)다.

## 데이터 기준일 (`content/config.json` → `dataVerified`)

`data/` 의 법령 연혁·설치기준을 국가법령정보센터 원문과 마지막으로 대조한 날이다. 이 날짜로

- 행의 **현행·종료·시행 예정**을 가른다(시계를 쓰지 않는다),
- 기준 페이지의 "데이터 기준일"과 "최종 수정일", 사이트맵 `lastmod`, JSON-LD `dateModified` 를 정한다
  (최종 수정일 = max(`dataVerified`, `standardsPublished`) — 첫 게시일보다 앞서지 않게),
- 현행 시행령·화재안전기준 판(기준일 이전 시행분 중 최신)을 고른다.

**빌드 검사:** 법령 연혁(`law_history_*.json`, `nfsc_history.json`)에 `dataVerified` 보다 늦게 공포된 행이 있으면 빌드가 멈춘다
(데이터를 바꾸고 기준일을 올리지 않은 것). 법령 반영 PR 은 `dataVerified` 를 대조한 날로 올리고 생성 결과를 함께 커밋한다.

## 프론트매터 형식

글 파일은 `---` 로 감싼 프론트매터와 Markdown 본문이다. 파일 이름이 URL 슬러그다(영문 소문자·숫자·하이픈, `index`·`feed`·`articles` 금지).

```markdown
---
title: 6층 이상 건물 스프링클러, 언제부터 모든 층에 설치하나요?
description: 검색 결과에 보일 한두 문장 (80~160자 권장)
date: 2026-09-27
updated: 2026-09-28
status: draft
tags: [스프링클러, 6층, 허가일]
related:
  - /standards/facility/sprinkler
  - /guide/sprinkler
sources:
  - label: 소방시설 설치 및 관리에 관한 법률 시행령 (대통령령 제35860호)
    url: https://www.law.go.kr/LSW/lsInfoP.do?lsiSeq=279911
faq:
  - q: 질문 한 줄
    a: 답 한 줄 (화면의 '자주 묻는 질문'과 FAQPage JSON-LD 에 같이 들어간다)
---
본문 (## 부터)
```

| 키 | 필수 | 규칙 |
|---|---|---|
| `title` | ○ | 페이지 제목·h1·og:title (40자 안팎 권장) |
| `description` | ○ | 메타 설명·요약문·RSS 설명 |
| `date` | ○ | 게시일 `YYYY-MM-DD` |
| `updated` | | 최종 수정일 (없으면 `date`, `date` 보다 빠를 수 없음). 화면의 "최종 수정일"·사이트맵 lastmod |
| `status` | ○ | `draft` \| `approved` — **approved 만 렌더링** |
| `tags` | | 문자열 목록 |
| `related` | | 사이트 경로 목록(확장자 없이). 승인된 글은 없는 경로·초안 글을 가리키면 빌드가 멈춘다 |
| `sources` | ○ (1개 이상) | `{label, url}` 목록, `url` 은 `https://` (법령은 law.go.kr 원문) |
| `faq` | | `{q, a}` 목록 — 있으면 화면에 보이고 FAQPage 도 붙는다(없으면 붙지 않는다) |

파서 규칙(YAML 부분집합): 값은 모두 문자열이다(숫자·불리언 변환 없음). `"…"`(JSON 문자열 규칙)·`'…'`(`''` 로 작은따옴표) 따옴표를 쓸 수 있다.
따옴표 없는 값은 줄 끝까지 그대로다(`title: Q&A: 무창층` 가능). 줄 끝 주석, 여러 줄 문자열(`|` `>`), `{…}`, 중첩 목록은
**지원하지 않고 오류로 멈춘다** — 조용히 잘못 읽지 않게. `#` 로 시작하는 줄은 주석. 알 수 없는 키(오타)도 오류다.

### 본문 문법 (Markdown 부분집합)

- 제목 `##` ~ `######` (`#` 은 h2 로 내려간다 — h1 은 제목 하나뿐), 문단, `**굵게**`, `*기울임*`, `` `코드` ``,
  `[글자](주소)`, 목록(`-` `*` `+`, `1.`), 중첩 목록, GFM 표(`|---|:---:|`, `\|` 로 칸 안의 파이프), 인용 `>`, 가로줄 `---`.
- 링크 주소는 `https://…`, `/사이트/경로`, `#앵커` 만. 외부 링크는 새 창 + `rel="noopener"`. 그 밖(`javascript:` 등)은 링크 없이 글자로 남는다.
- HTML 태그는 통과시키지 않는다(글자로 보인다). 이미지, 코드 블록, 밑줄(`_`) 강조, setext 제목, 각주는 지원하지 않는다.
- 주의: 줄 맨 앞의 `1.` ~ `999.` 는 번호 목록이다(`2024. 12. 31.` 처럼 네 자리는 괜찮다). `---` 한 줄은 항상 가로줄이다.

## 초안 → 검수 → 승인 → 게시

1. **초안** — `/content-draft` 스킬(`.claude/skills/content-draft/SKILL.md`)이 `content/topics.json` 에서 주제를 골라
   `status: draft` 글을 쓰고, `origin/main` 에서 만든 브랜치에 커밋해 **Draft PR** 을 연다. 주제의 `status` 는 `draft`, `post` 에 파일 경로.
2. **검수** — 글마다 검수 페이지(소유자의 비공개 claude.ai 아티팩트)에 항목을 올린다. 데이터 형식은 `docs/review-page.md`
   (`batches/content-YYYYMMDD`, `items/content-YYYYMMDD-<n>`, `kind: "post"`). **검수 페이지 URL 은 저장소에 적지 않는다** —
   소유자의 Claude 메모리에 있다. 소유자는 `approve`(발행) / `revise`(고쳐서 다시) / `reject`(발행 안 함) / `later` 를 고른다.
3. **반영** — `/review-apply` 가 결정을 PR 에 반영한다: approve → `status: approved`(+`updated`) 후 빌드·커밋,
   reject → 초안 삭제, revise → 메모대로 고친 뒤 항목을 다시 올린다.
4. **게시** — 소유자가 PR 을 병합하면 Cloudflare Pages 가 `main` 을 배포한다. 초안인 채로 병합돼도 게시되지 않는다.

초안은 커밋된 결과에 렌더링되지 않으므로 Cloudflare 브랜치 미리보기에도 없다. 미리보기는 `--drafts --out <저장소 밖 폴더>` 로 만든다
(초안은 noindex + "초안 — 검수 전" 표시, 사이트맵·RSS 에는 들어가지 않는다).

`content/topics.json`: `{id, keyword, type: guide|qa|news, intent, priority: 1~3, status: todo|draft|published|dropped, post?, notes?}`.
`notes` 는 조사 출발점일 뿐 근거가 아니다.

## 품질 게이트

- **얇은 페이지 금지**: 기준 행이 `MIN_INDEXABLE_ROWS`(2) 미만인 기준 페이지는 `noindex, follow` + 사이트맵 제외.
  기준 행이 없는 시설은 페이지를 만들지 않는다. 승인된 글이 없는 목록 페이지(`/news/` 등)도 noindex.
  (이 PR 기준 시설 페이지 40개 중 7개가 noindex: 화재알림설비·객석유도등·소공간용 소화용구·연소방지재·방화벽·비상용 승강기·유효 조치)
- **지어내지 않는다**: 기준 페이지는 데이터 문구만 보여 주고 "원문 요약"으로 표시한다. 글의 법령 문장은 모두 출처(조문·원문 링크)가 있어야 하고,
  인용은 원문 그대로, 해석은 "(해석)"으로 밝힌다. 통계·금액·기한은 원문에서 확인한 것만.
- **이스케이프**: 데이터·프론트매터·본문의 모든 글자는 이스케이프된다. 생성 페이지에는 인라인 이벤트 핸들러가 없다
  (헤더는 components.js 가 실행 중에 넣는다). JSON-LD 안의 `<` `>` `&` 는 유니코드 이스케이프(`\u003c` 등)로 바꿔 넣는다.
- 테스트가 모든 생성 페이지의 태그 짝, h1 하나, 확장자 없는 canonical, 외부 링크 `rel="noopener"`, 같은 페이지 앵커,
  **사이트 내부 링크가 실제 페이지·파일을 가리키는지**, 조회 화면 직접 입력 용도 연결(index.html·main.js)과의 일치를 확인한다.

## SEO 규칙

- **E-E-A-T**: 모든 페이지에 출처(law.go.kr 원문 링크), 보이는 "최종 수정일", 검수 표시(승인된 글은 "운영자 검수 완료",
  기준 페이지는 "소방체크 기준 데이터로 생성"과 데이터 기준일), 법적 효력 없음 안내.
- **FAQ 스키마는 화면에 보일 때만.** 기준 페이지에는 FAQ 를 자동으로 만들지 않는다.
- 제목·설명: 제목은 핵심 검색어를 앞에(40자 안팎), 설명은 답을 먼저. 본문은 답 먼저 → 근거 인용 → 적용 시점(허가일·신청일) → 실무 확인점.
- 내부 링크: 글의 `related` 는 검사된다. 기준 페이지끼리(용도 ↔ 시설, 허브) 서로 잇고, 모든 페이지가 조회 도구(`/`)로 안내한다.
- 사이트맵은 생성된다: 손으로 쓴 페이지는 canonical 이 있고 noindex 가 아닌 것(`index.html`, `pages/*.html`, `guide/*.html`)을 찾아
  `content/static-pages.json` 순서로 넣는다. `lastmod` 는 그 파일의 값과 페이지 JSON-LD `dateModified` 중 늦은 날, 근거가 없으면 비운다.
  이용약관·개인정보처리방침은 noindex 라 빠진다(이전 수작업 사이트맵에는 있었다). 손으로 쓴 페이지의 `dateModified` 를 바꾸면 다시 생성한다.

## 다른 작업과의 연결

- **주간 법령 감시 → `/law-update`**: 데이터가 바뀌는 법령 반영 PR 에서는 ① `content/config.json` 의 `dataVerified` 를 원문 대조일로 올리고,
  ② `node scripts/content/build.mjs` 로 기준 페이지를 다시 만들어 ③ 결과를 같은 PR 에 커밋한다(`--check` 가 빠뜨림을 잡는다).
  그 PR 이 병합되면 `/content-draft` 로 **법령 개정 소식 초안**(news)을 쓴다 — 인용은 law-update PR 의 원문 인용을 다시 확인해 쓴다.
- **`js/components.js` 의 푸터**는 생성 페이지에 미리 넣어 두므로(스크립트 없이도 링크가 보이게) 푸터를 바꾸면 다시 생성한다.
- **index.html 직접 입력 용도 목록이나 main.js 용도 연결**을 바꾸면 `MANUAL_PURPOSE_BY_TYPE`(lib/config.mjs) 검사가 실패할 수 있다 — 함께 고친다.

## CI

이 브랜치에는 워크플로가 없다. 법령 감시 PR 이 `.github/workflows/law-data-check.yml` 을 추가하면 아래 단계를 넣고,
`paths` 에 `content/**`, `css/content.css`, `js/components.js`, `index.html`, `pages/**`, `guide/**`, `sitemap.xml`,
`standards/**`, `news/**`, `qa/**` 를 더한다(데이터가 아니어도 생성 결과가 바뀌는 파일).

```yaml
      - name: 콘텐츠 생성기 테스트
        run: node --test scripts/content/test/*.test.mjs
      - name: 생성 결과가 최신인지
        run: node scripts/content/build.mjs --check
```
